Privacy

Privacy model

Presspeech transcribes locally: it has no Presspeech-operated analytics service, accounts, crash reporter, transcript sync, or cloud transcription endpoint. However, the published Windows 0.1.12 prerelease does not disable Hugging Face Hub/Transformers usage telemetry during model downloads; see the model-download entry in the network inventory below. That dependency-generated telemetry is not audio or transcript upload. The pinned Windows 0.1.12 Hub 1.29.0 client may also look up its agent-harness registry when the local cache is missing or stale and may label model-request metadata from inherited agent markers; details are in the inventory below. The release loader also leaves Hugging Face's default implicit authentication enabled: if HF_TOKEN or HUGGING_FACE_HUB_TOKEN is available in the environment, or a token is saved in the local Hugging Face cache, a model request may include it. It honors inherited HF_ENDPOINT and HUGGINGFACE_CO_STAGING settings, which can change the request destination; if HF_HUB_USER_AGENT_ORIGIN is set, its value is added to request metadata. An available token may therefore accompany a request to that configured endpoint. These public models do not require an account token. Hugging Face’s Hub authentication guidance explains that saved or environment-provided tokens are used implicitly by default. Its release source pins hf-xet 1.6.0, which predates the later separate Xet transfer-telemetry implementation; we do not claim that 0.1.12 sends those Xet reports. Upcoming Windows 0.1.13 adds runtime-verified Hub telemetry and implicit-authentication opt-outs, fixes the public endpoint/staging settings, removes the inherited User-Agent origin, and bypasses hf-xet; do not attribute these controls to 0.1.12.

Windows 0.1.12 package vs. launch: downloading the installer and checksum from GitHub does not make a model request; the selected model download starts when Presspeech launches. If you install 0.1.12 but choose to wait for 0.1.13, leave Launch Presspeech unchecked on the installer's final screen.

Already used Windows 0.1.12? If a model download ran with a token available and an inherited HF_ENDPOINT or staging setting may have sent it to a destination you do not trust, treat the token as disclosed to that destination. Revoke the token and create a replacement at Hugging Face Access Tokens; do not include token values in logs or support requests.

Before installing or launching macOS 0.3.8: its model-download requests may include a Hugging Face token inherited by Presspeech, although the public model needs no token. If a token may be present in the environment that launches Presspeech—or you are unsure—wait until macOS 0.3.9 is published. Downloading the macOS ZIP from GitHub does not make a model request; the first download of a missing model starts when the app launches, so you can keep the downloaded app unopened while waiting. Dictation audio and transcripts are not sent in these requests. Upcoming macOS 0.3.9 removes inherited Hugging Face credentials from its own process before FluidAudio can read them. See the version-specific network inventory.

Already used macOS 0.3.8? The concern is limited to a possible Hugging Face token on a model-download request; dictation audio and transcripts are not included. If your local model is working, leave its cache in place. A later download—including an integrity retry or cache reset—may make another request. When you can choose the timing, wait until 0.3.9 is installed before downloading again; it removes inherited Hugging Face credentials from Presspeech's download process. Do not include token values in support reports.

What happens to the audio

Transcript handling

In memory

Audio is captured while the hotkey is active, transcribed locally, then discarded.

Paste at cursor

The finished text normally goes through the platform clipboard and a synthetic paste shortcut. On macOS, Presspeech falls back to direct Unicode key events if clipboard paste setup fails.

Clipboard persistence

Each recording is bound to the window focused when it began. If focus changes or Presspeech cannot verify the same destination, it leaves the transcript on the clipboard for deliberate manual paste instead of risking delivery to the wrong window. macOS leaves the transcript on the pasteboard by default. In macOS 0.3.8 and later, the off-by-default Keep Previous Clipboard for Manual Restore option keeps an eligible complete previous clipboard snapshot only in memory for up to five minutes. A snapshot is limited to 64 MB and 256 representations; no partial snapshot is offered when a limit is exceeded or a representation is unavailable. Consecutive dictations keep the original deadline. It restores only after you choose Restore Previous Clipboard…, verify the paste arrived and confirm, while clipboard ownership still matches. Expiry, another copy, disabling the option or quitting discards the saved snapshot without rewriting the clipboard. The retired automatic timer preference does not enable this retention option. Confirmation is a user decision, not an operating-system acknowledgement. See the recovery guide. Builds containing local-only transcript clipboard writes mark automatic-paste, recovery, recent-transcript and scratchpad copies as current-device-only and transient while keeping them available to local Command-V. They retain every item and representation when restoring a previous clipboard, but republish the snapshot for the current device only because its earlier cross-device scope cannot be recovered. Windows leaves the transcript on the clipboard until something else is copied. Upcoming Windows 0.1.13: unsuccessful or uncertain delivery keeps a recovery copy only in process memory until an explicit verified Copy, Discard, or Exit. The keyboard-accessible Delivery Recovery window does not display or implicitly copy the words; a blocked hotkey or another launch only brings the window back. Depending on where delivery became uncertain, text may already be in the field or clipboard. Recording waits for review. Every normal or recovery clipboard write first adds Microsoft's history/cloud exclusion format, so Windows is instructed not to retain or sync the item through Clipboard History or Cloud Clipboard. The current item remains available to Ctrl+V and other local clipboard readers; no transcript contents are written to logs, settings or recovery files.

Operating-system clipboard services

“No transcript sync” describes Presspeech itself, not every service that monitors the general clipboard. On macOS 26 or later, enabled macOS Clipboard History in Spotlight makes earlier copied items searchable; Apple notes that sensitive information may appear there and provides Clipboard → More → Clear History. With Handoff enabled, macOS Universal Clipboard can make general pasteboard content available on nearby Apple devices. macOS 0.3.8 can expose transcript entries to that service. Builds containing local-only transcript clipboard writes use Apple's currentHostOnly option for every transcript write, preventing those entries from becoming available on another device while preserving local paste. Standard transient, auto-generated, and concealed markers ask cooperating clipboard managers not to archive or visibly expose the entries, but macOS Clipboard History, Third-party clipboard managers that ignore those advisory markers, and other local readers remain separate boundaries. Published Windows 0.1.12 writes can be retained by Windows Clipboard History or synced through its cross-device setting. Upcoming Windows 0.1.13 uses Microsoft's documented clipboard exclusion format to opt every dictation write out of both services. Review local clipboard software and operating-system history settings before sensitive dictation.

No transcript logs

Logs include operational status, error categories, timings, and counts. Presspeech does not write transcript, audio, or dictionary/correction contents to the log. macOS 0.3.8 and Windows 0.1.12 can log exact audio-device labels; builds containing microphone log minimisation omit those labels from app-authored microphone events. Some operating-system or library errors elsewhere in the local log can still contain private names or paths, so review any excerpt before sharing it.

Five call types, fully listed

Network calls

This is the complete network surface of Presspeech itself and its install/update path. Operating-system clipboard sync and third-party clipboard managers are separate services described above.

Presspeech does not collect or store your IP address. As with any network connection, the destination service can see the source IP address and request timing, and network intermediaries may also observe connection metadata. A fixed User-Agent and the absence of an app-added identifier do not make a request anonymous; GitHub describes IP addresses and request times as service-usage information in its privacy statement.

Sandbox surface

Permissions and entitlements

The notarised macOS app uses two hardened-runtime entitlements: audio input and microphone. macOS also requires user-granted Accessibility and Input Monitoring permissions for the hotkey and paste workflow. Input Monitoring is a broad system grant that can expose typed keys. Presspeech's event tap requests keyboard events only to detect the configured hotkey and Escape to cancel an active recording; it does not inspect mouse or trackpad events, and other keys pass through without their values being saved, logged, or sent. See Apple's Input Monitoring guide before deciding.

The macOS app does not add JIT, unsigned executable memory, library-validation, network-client, contacts, calendar, location, camera, or file-provider entitlements.
