Target-app check

Test Presspeech with one app

Automatic paste depends on the destination and its focus behavior. Use blank disposable fields to check one exact app and version before relying on it for real work. The check records outcomes, never your words.

Published-build privacy check (24 September 2026): The current downloads are macOS 0.3.8 and Windows 0.1.12. Both start a missing-model download on launch. The macOS request may include an inherited Hugging Face token; the Windows request may send Hugging Face usage telemetry or a locally available token, with additional routing and proxy risks. Read the macOS model-download warning or Windows model-download warning before launching or triggering a model download. If you are unsure about those version-specific risks, wait for 0.3.9 or 0.1.13 to be published rather than launching solely for this check. If your model is already ready, do not reset its cache or switch models for this protocol.

Scope

Separate insertion from recognition

Presspeech binds each recording to the window where it began. It should paste only when it can still verify that destination. A focus change should avoid insertion and leave a route to deliberate manual recovery, but the clipboard state is version-specific. macOS and published Windows 0.1.12 normally leave a copy on the clipboard; upcoming Windows 0.1.13 can keep it only in memory until Delivery Recovery → Copy for Manual Paste is chosen. On macOS, if Presspeech detects another copy replacing the clipboard during delivery, it stops and preserves that newer copy; 0.3.8 shows Couldn't paste, while builds with revised wording say Delivery uncertain. A failed input event does not prove that no text reached the destination, so inspect the target before retrying or using recovery. After a copied notice, a later copy can replace the transcript without updating that notice; use Command-V only if the clipboard still holds the dictation, or use Copy Last Transcript when available. Revised macOS copy notices make this condition explicit.

macOS 0.3.8 checks the original window, not the field or browser tab within it. The 0.3.9 implementation also compares the focused Accessibility control when an app exposes one at recording start. If no control is exposed then, or two fields reuse one identity, a same-window move can still send the transcript to the new focus. Keep the original field and tab focused until insertion or a recovery notice appears. The separate-window checks below do not establish safety for same-window moves.

This is a delivery check, not a transcription-quality test. The recognized wording can differ from what was spoken and still pass: the question is whether the same finished transcript reaches the intended field once, or is recovered safely without reaching another field.

Prepare safely

Before testing

  1. Finish Presspeech setup

    Read the published-build privacy check above before launching or downloading a model. Use the current official build. On macOS, this baseline requires 0.3.8 or later; update before testing if the About window shows 0.3.7. Confirm the model is ready, the microphone and hotkey checks pass, and Try Dictation works first.

  2. Open two disposable fields

    Use one blank field in the target app and one blank field in a local scratch app. Never use a production message, document, account, command shell, or field where pasted text can submit, send, or execute. Test a remote/virtual environment or terminal-based editor only when it is isolated, disposable, and non-executing; otherwise skip that target.

  3. Use harmless, distinct phrases

    Create a different phrase for every attempt so stale or duplicate delivery is visible. Do not use names, credentials, commands, customer data, or text from real work.

    Optional eight-phrase prompt

    If English suits the selected language hint, use these in order: amber rabbit one; blue otter two; copper robin three; green badger four; ivory falcon five; purple fox six; silver heron seven; yellow turtle eight. Otherwise use the same colour-animal-number pattern in the test language. Recognition accuracy is not scored; compare the finished target text with the scratch paste. Never add either version to the public report.

  4. Make clipboard behavior comparable

    On macOS 0.3.8 and later, leave Keep Previous Clipboard for Manual Restore off for this baseline. Published Windows 0.1.12 leaves the finished transcript on the current clipboard. Upcoming Windows 0.1.13 leaves the previous item unchanged for an already-known invalid target; do not assume a recovery notice means the transcript is on the clipboard. Its actual dictation clipboard writes are marked for exclusion from Windows Clipboard History and Cloud Clipboard; published 0.1.12 does not mark them. macOS 0.3.8 can expose transcript entries to macOS Universal Clipboard; disable Handoff if the harmless test text must stay on the Mac. Builds containing local-only transcript clipboard writes prevent Universal Clipboard transfer while preserving local Command-V. Apple's Screen Sharing has a separate Edit → Use Shared Clipboard setting; those transcript writes are not a tested guarantee against that remote transfer. Turn shared clipboard off if you do not intend to transfer test text to the remote Mac. If macOS Clipboard History in Spotlight is enabled on macOS 26 or later, clear it after the check if you do not want the text retained there. Also disable third-party clipboard managers if you do not want the test text retained elsewhere.

  5. Check the target's own Paste shortcut

    Copy a harmless marker by ordinary means, then use physical Command-V on macOS or Control-V on Windows once in that same blank target field. Confirm it appears exactly once and clear the field before dictating. This is a target-app shortcut baseline, not a Presspeech result or one of the eight worksheet attempts. If it fails, do not score that target as a Presspeech paste pass or guess that Presspeech caused the failure; keep a local note of the target version and try another safe target. A working context-menu Paste does not establish that the keyboard shortcut works.

  6. Record versions, not private context

    Note the Presspeech, operating-system, and target-app versions. Classify the target as native, browser/web editor, Electron/Chromium, terminal, remote desktop/virtual machine, or elevated Windows app, and record the generic field type (for example, plain text, rich text, or browser content editor). Note the active keyboard layout/input source only if it differs from your usual layout or helps explain an outcome; record its public name, never typed content. Omit account, server, document, tab, form, and window names.

Checks 1–5

Keep the target focused

Plan five attempts with a different harmless phrase each time. Stop early if an attempt is incorrect or unsafe; do not repeat it just to fill the worksheet.

  1. Start in the blank target field

    Keep its window focused from the start of recording until Presspeech finishes. Do not copy anything or allow a clipboard tool to replace its contents during delivery.

  2. Dictate once, then inspect the target

    Note whether one copy appeared and whether Presspeech showed a version-appropriate recovery notice.

  3. Compare the finished text using the right recovery route

    First inspect the target field. After an automatic paste with no recovery notice, paste the current clipboard into the separate local scratch field before copying anything else and compare the complete text, including its suffix. After a macOS copied notice or published Windows 0.1.12's Transcript copied, not pasted, check the clipboard in the scratch field before manual paste. The notice reflects a copy at completion, not a guarantee that a later clipboard change left the transcript current. After upcoming Windows 0.1.13's Delivery Recovery notice, do not treat the current clipboard as the transcript: choose Copy for Manual Paste explicitly, then paste that copy into the scratch field. The prior clipboard item may still be current. On macOS, a Couldn't paste or Delivery uncertain warning also does not prove the clipboard contains the transcript or that the target received nothing; inspect the target, then use Copy Last Transcript if offered. Remove any partial target text before pasting a full recovery copy. If no recovery copy is available, record a failed delivery; deliberate recovery never turns an attempt into an automatic-paste pass.

  4. Classify one outcome

    Use the definitions below, then clear both disposable fields before the next attempt.

Pasted once

The target received one copy, no recovery notice appeared, and its text matches the scratch copy, including the configured space or newline suffix.

Recovered safely

The target received nothing, Presspeech showed the version-appropriate recovery notice, and the scratch paste recovered the complete finished transcript—directly from a copied notice or after explicit Delivery Recovery Copy on Windows 0.1.13.

Incorrect or unsafe

Text was stale, partial, duplicated, unavailable, delivered elsewhere, or paste failed without a recovery notice. Stop testing, mark this slot incorrect or unsafe, and mark every remaining steady-focus and focus-change slot not completed. Do not retry in a real document.

Not completed means an attempt was not run. If you cannot continue for another reason, classify each unrun slot that way; do not call a completed failure not completed. An early stop is not a passing five-attempt baseline.

If you know another copy changed the clipboard during delivery, and it prevented classification without an incorrect or unsafe result, record it as an interruption under Relevant conditions and repeat with a fresh harmless phrase if it remains safe to continue. Exclude only those safe, known, unclassifiable interruptions from the five scheduled check slots; count completed pasted-once and recovered-safely outcomes. A stale, partial, duplicate, misdirected, or unrecoverable result is Incorrect or unsafe even when the clipboard change explains it: count that completed attempt and stop. Never exclude an unexplained failure.

Keep recovery separate from automatic paste. Manual-paste recovery is safe behavior, but counting it as an automatic-paste pass would hide app classes where insertion is consistently unavailable. The four aggregate steady-focus counts, including not completed, should total five.

Checks 6–8

Move focus before dictation finishes

Use blank disposable fields in two separate windows. Start dictation in the first window, move focus to the second, then finish. In hold mode, move before releasing the hotkey; in toggle mode, move before the stop press.

With no intervening clipboard change

  • No text is inserted into either field.
  • Presspeech shows the version-appropriate recovery notice.
  • The complete transcript is available for deliberate manual paste. On upcoming Windows 0.1.13, choose Delivery Recovery → Copy for Manual Paste before treating the clipboard as the transcript.

Plan three attempts

Record known clipboard-change interruptions separately as above. For an Electron/Chromium app, use two separate windows of that same app for at least one attempt. Same-process windows are a distinct identity check; tabs or fields in one window are not a substitute.

Classify each slot as copied for manual paste without inserting anywhere, inserted into a field, no insertion, but recovery failed, or not completed. The first category includes an explicit, verified Copy from Windows 0.1.13 Delivery Recovery; it does not imply the app copied automatically. Recovery failed means a completed attempt inserted nowhere but the notice or complete transcript was unavailable; it is an incorrect result, not an unrun check. Do not exclude insertion or failed recovery as an interruption merely because another copy changed the clipboard. The four counts should total three.

An older seven-count draft with five classified steady-focus attempts can add Steady-focus not completed: 0. An older six-count draft may combine failed recovery and unrun focus-change slots as Other or not completed. If that count is zero, both new focus-change counts are zero. If it is nonzero, do not guess or present the draft as a comparable eight-count baseline. Keep it private and, if safe, rerun the protocol using the current categories.

Stop on unexpected insertion or failed recovery. Mark the completed slot as Inserted into a field or No insertion, but recovery failed, then mark each later unrun slot Not completed. Text reaching either test window or any unrelated destination is a safety failure; do not retry in a real document. Use the private reporting route if the behavior could expose or execute sensitive content.

Optional macOS observation

Check a tab switch separately

The eight checks use separate windows; they cannot establish safety when a browser switches tabs inside one window. The macOS 0.3.8 implementation checks only the window, so this is already a known limitation of that build. Do not repeat it to claim a new 0.3.8 safety result. If you have a macOS 0.3.9 or later build with focused-control checks, this optional observation can help identify a browser/version that still needs native qualification.

Run it only after an eight-check baseline with no unsafe result. Use two blank, non-submitting fields in two tabs of the same browser window, and harmless disposable text. First verify ordinary physical Command-V in both fields and clear them; skip this observation if either shortcut fails. In toggle mode, start one dictation in the first tab, switch to the second before stopping, and keep it focused until Presspeech finishes. If switching safely while recording is not possible, skip the observation. Inspect both fields before copying, pasting, or retrying. Do not switch back before delivery or test in a real form, chat, or command window.

Classify this one attempt separately: safe recovery means neither field received automatic text, a recovery notice appeared, and the complete transcript was available for deliberate manual paste by the version-appropriate route above. Insertion into the second tab, missing recovery, or an unverified clipboard item is unsafe; stop. Record only safe recovery, unsafe insertion or failed recovery, or not run, with public browser and Presspeech versions and a generic field type under Relevant conditions. Never share tab titles, URLs, field contents, transcripts, or clipboard data. Do not add this attempt to the eight worksheet counts or Overall result. A safe community observation is not a general tab guarantee or a substitute for the three native release-gate trials; an unsafe result matters even when the eight-check block passed.

Interpret the result

Keep platform boundaries separate

Clipboard behavior

Leave optional macOS clipboard restoration off for this baseline. On macOS 26 or later, enabled macOS Clipboard History in Spotlight can make earlier copies searchable. macOS 0.3.8 can make transcript entries available through macOS Universal Clipboard; builds containing local-only transcript clipboard writes prevent that transfer. Published Windows 0.1.12 does not opt out of Windows clipboard history or cross-device sync. Upcoming Windows 0.1.13 opts its writes out of both Windows services. third-party managers remain a separate local boundary on either platform. Review the clipboard privacy boundary.

Elevated Windows apps

Windows restricts synthetic input to targets at an equal or lower integrity level. A normally running app therefore cannot send the paste shortcut into a target running as administrator. Published Windows 0.1.12 shows a copied/manual-paste notice; upcoming 0.1.13 offers Delivery Recovery without replacing the previous clipboard item. Do not elevate Presspeech as a workaround.

Remote and specialist targets

Remote desktop, virtual machine, terminal-based editor, browser editor, and assistive-technology paths are useful reports only when the field is isolated, disposable, and cannot submit or execute a paste. An ordinary command-shell prompt is outside this community protocol. Identify the class without sharing host names, commands, account names, document titles, or private paths.

Optional remote clipboard handoff check: the eight worksheet slots switch to a local scratch field after each attempt. Returning to a remote viewer can refresh a separately synchronised clipboard, so passing counts do not establish consecutive delivery while that viewer stays active. If the protocol's harmless-marker physical Paste baseline works in a blank, non-submitting remote field with clipboard sharing permitted and intentionally enabled, and no unsafe result has occurred, make up to three additional dictations with distinct harmless markers. Keep the viewer and same remote field active; clear the field using only remote controls. Do not switch to a local scratch field, copy, or reactivate the viewer between attempts. Inspect each result and stop on stale, missing, partial, duplicated, or misdirected text, or a recovery notice. Afterward, compare the last result with a local scratch paste only if that build leaves the transcript on the clipboard or offers an explicit recovery Copy.

Report the remote client/public version, local and guest OS versions, clipboard-sharing state, number of additional attempts, any anomalous result or recovery notice, and whether the final scratch comparison matched or was unavailable under Relevant conditions—not in the eight worksheet counts. Omit markers, transcripts, hostnames, clipboard contents, and screenshots. This supplement can expose stale transfer but cannot independently verify the exact transcript for earlier attempts or replace native qualification. If not run, do not claim continuous-focus remote delivery passed. The worksheet's Overall result describes only its eight slots; a passing block does not override an anomaly in this supplement.

Clipboard restoration regression

If previous clipboard content is inserted, turn restoration off, remove the unintended text, and follow the recovery guide. Report that as a bug rather than a compatibility pass.
